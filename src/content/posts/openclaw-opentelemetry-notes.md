이 글은 OpenClaw를 운영하면서 OpenTelemetry(OTEL) / Tempo를 붙여보려 했던 시도를 **운영 기록**으로 정리한 문서다.

목적은 하나였다.

- “딜레이/누락/크론 스킵” 같은 운영 이슈를 로그가 아니라 trace로 더 빨리 분리하고 싶다.

결론은 이렇게 정리한다.

- OTEL 자체는 좋은 도구지만, 개인/홈서버 운영에서는 관측 스택이 본체보다 커지는 순간부터 역효과가 난다.
- 지금 단계에선 **운영 안정성 우선**으로 두고, OTEL은 “필요한 순간에만 켜는 옵션”으로 남기는 게 맞았다.

## 1) 배경: 왜 OTEL을 붙이려 했나

OpenClaw는 다음이 한 프로세스/런타임 안에서 같이 돌아간다.

- 채널 인바운드/아웃바운드(Telegram 등)
- 에이전트 턴 실행
- 툴 호출/승인 플로우
- 스케줄러(cron/heartbeat)

운영 중 체감 이슈는 보통 이런 형태로 나타난다.

- 응답이 가끔 늦다
- 크론이 가끔 건너뛴 것 같다
- 특정 메시지가 누락된 것 같다

이런 문제는 “어느 단계에서” 늦었는지를 알아야 해결이 된다.

그래서 처음 목표는 아래 span들을 잡는 거였다.

- turn(메시지) 단위 trace
- tool call span
- cron/heartbeat run span
- channel inbound/outbound span

## 2) 시도: Tempo/Collector/Exporter 구성

시도는 전형적인 OTEL 파이프라인으로 갔다.

1) Tempo(또는 Jaeger)
2) OTEL Collector
3) OpenClaw exporter → OTLP

여기서 바로 현실적인 문제가 발생한다.

- 네트워크/포트/프로토콜(HTTP vs gRPC)
- 샘플링/배치
- collector 설정(YAML) 디버깅

즉, **관측을 붙이려다가 관측 스택을 운영하는 일이 본업이 되는** 상태로 기울기 시작했다.

## 3) 판단: 운영 안정이 먼저다 (중단/롤백)

운영 관점에서 중요한 질문은 이거였다.

- OTEL을 붙여서 “지금 겪는 문제”가 더 빨리 해결되는가?

이때 내 답은 “아니다”였다.

- 문제 원인이 OpenClaw인지, exporter/collector/tempo인지 분리가 어렵다
- 실패 시 로그가 더 지저분해진다
- 관측 I/O 자체가 딜레이를 악화시킬 수 있다

그래서 OTEL 디버깅은 중단했고, OpenClaw 설정에서 OTEL 관련 구성을 제거해서 기본 운영을 단순화했다.

(운영 메모 기준으로 2026-02-13에 OTEL/Tempo 디버깅을 중단하고 관련 설정을 제거했다.)

## 4) 현재 운영 원칙 (OTEL 없이 먼저 하는 것)

OTEL을 다시 붙이기 전에, 아래가 체감 개선에 더 효과가 컸다.

- 로그 타임존/포맷 통일(로컬 타임스탬프)
- 크론/하트비트 신뢰성 설정 재점검
- “즉시 ACK → 완료 결과” 운영 패턴 정립(사용자 체감 개선)

## 5) 다음에 다시 OTEL을 붙인다면: 재도전 기준

다시 시도할 때는 “전부 계측”이 아니라, 목표를 아주 좁히는 방식으로 간다.

- 목표 예시 1: “cron이 skip 되는지”만 확인
- 목표 예시 2: “outbound가 어디서 막히는지”만 확인

그리고 운영에서 지켜야 할 룰:

- 기본은 low sampling
- 특정 sessionKey/agentId만 full sampling
- 관측 스택이 본체보다 커지는 순간 즉시 중단(재도전은 나중에)

## 정리

OTEL/Tempo는 분명 강력하다.

하지만 개인/홈서버 운영에서는 “도입 자체”가 목표가 되면 바로 비용이 폭발한다.

그래서 지금 단계의 결론은 이거다.

- 운영 안정이 먼저
- 관측은 필요할 때, 작게, 켰다 끌 수 있게
